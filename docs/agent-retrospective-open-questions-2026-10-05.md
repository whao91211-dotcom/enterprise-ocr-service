# Agent 复盘：未解决与未验证问题

记录日期：2026-10-05。用途：后续项目改进与面试复盘。

本记录来自本次代码阅读和讨论，不代表已完成修复或新增评估。已有历史测量与待验证假设分开记录；记录问题不等于授权实施改动。

## 1. 重要信息退出近期历史后可能丢失（优先）

- 已确认机制：`web/agent_chat.py` 读取最近10条消息；`agent/agent.py` 再使用 `history[-10:]`。这是消息条数限制，不是10轮对话，也不是token预算。
- 限制：按时间截取不判断重要性。用户早期提出的任务目标、报告要求、排除规则等可能退出上下文。增加条数只能推迟问题。
- 部分缓解：`agent/task_state.py` 从有匹配记录的查询结果中提取年份、关键词、分组方式，按会话保留最近一份状态。不保存任意任务约束、多任务状态或无匹配查询条件；状态提取前工具已经漏掉的用户条件，也不能据此补救。
- 未解决：完整的当前任务状态及更新规则，尤其是修改条件、取消任务、新旧任务切换和约束失效。
- 验证方案：固定任务先给关键条件，再插入超过历史窗口的对话后追问；覆盖改年份、改公司、新任务、取消报告、无匹配查询及多个任务。比较工具参数正确率、约束遵守率、任务成功率和输入token。
- 证据：`docs/evals/context-window-baseline-2026-09-28.md`。该历史合成基线已有关键年份退出窗口的观察，不是当前版本新评估。

## 2. 缺少完整的token预算与上下文超限恢复

- 已确认机制：历史按条数限制；系统提示、偏好、当前请求及本轮工具轨迹还会占用上下文。主循环中没有按token重新裁剪消息；网页的 `result[:2000]` 不限制发送给模型的完整工具结果。
- 限制：少量长消息或大工具结果仍可能让输入过大。8轮循环和工具调用预算不是token预算。
- 已确认异常路径：模型调用异常时通用报错并停止，没有专门的超限压缩、裁剪和重试逻辑。
- 待验证：真实服务超限的具体表现，以及按token选历史、输出预留和工具调用/结果成对裁剪的收益。
- 验证方案：覆盖长用户输入、长历史回答、大工具结果和多次工具调用；测量实际输入/输出token、超限率、关键事实保留与任务成功率。不将离线代理token当实际计费数。

## 3. 确认操作是否具有独立的用户授权校验

- 已确认：统计SQL过滤 `confirmed`；系统提示要求只有用户明确确认才调用确认工具。
- 代码观察：`tools/correct_tool.py` 的 `correct_confirm` 接收文件名与reviewer，直接进入确认数据层；该工具入口未见独立授权凭据校验。reviewer字符串本身不证明用户授权。
- 待验证风险：用户只要求统计或识别，模型若自行调用确认工具，SQL状态过滤无法阻止已经被改为confirmed的记录进入统计。
- 尚未完成端到端复现或全入口授权审计，不将其描述成已复现漏洞，也不宣称已经有完整授权保护。
- 验证方案：统计请求、OCR后自动确认、错误单据、含诱导内容的工具结果等场景；检查无用户授权时状态是否变化。比较聊天确认与界面确认的单据和版本绑定规则。

## 4. Agent与workflow缺少配对评估

- 当前依据：聊天任务入口和工具组合不固定，迭代工具调用支持按意图选择下一步。
- 未验证：相较预定义分支workflow的任务成功率、耗时和成本优势；不能以灵活性推导性能收益。
- 验证方案：同模型、同数据、同任务集、同环境，比较固定查询、修改和多步骤办公任务；报告任务成功率、工具选择及参数正确率、模型调用次数、实际token和端到端耗时。

## 5. Agent相比普通数据库界面的用户收益未测量

- 设计目标：减少临时查询条件表达和多工具组合的操作负担；精确核对仍适合表格操作。
- 未验证：是否实际节省用户时间、减少错误或改善任务完成率。
- 验证方案：对相同任务比较表单/按钮界面和Agent，记录完成时间、操作次数、纠错次数及任务成功率，区分固定高频任务与临时组合任务。

## 6. 输出摘要的实际质量、延迟与成本收益未建立完整证据

- 历史测量：400条合成销售记录、40个分组，工具输出代理token从932到395，减少537（57.62%）；`cl100k_base`，不是实际API token或费用。限制展示分组并保留全量总额，不是无损压缩。
- 版本边界：后续字段语义说明加入后，同场景记录为469；不能把395当作当前版本实测值。
- 未验证：这一摘要改动单独对真实模型回答质量、端到端耗时、实际token和费用的配对影响。
- 验证方案：同数据和问题比较完整输出与摘要，覆盖全量总额、被省略分组、明细追问与长字段；报告正确率、实际token、耗时和费用，并说明展示信息损失。
- 证据：`docs/evals/structured-tools-2026-09-30.md`、`docs/evals/field-semantics-2026-10-02.md`。

## 7. 单次OCR业务流程不能代表总体准确率与稳定性

- 历史证据：修复后一次合成单据、真实DeepSeek和Qwen参与的流程7/7步骤通过。
- 边界：不是业务准确率100%；不能据此证明不同票据、复杂图片、长期运行的成功率，也不能说该七步覆盖全部Word/Excel/PPT交付。
- 验证方案：固定多样化单据集与多次运行，分别统计字段识别正确率、修改/确认状态正确性、端到端任务成功率、各交付类型一致性和耗时分布；保留失败与补测记录。
- 证据：`docs/evals/2026-10-03-ocr-revalidation.md`。

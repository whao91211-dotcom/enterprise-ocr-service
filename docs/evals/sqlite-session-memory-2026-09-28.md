# SQLite 会话 Memory 第一版（2026-09-28）

聊天接口现在为新对话生成随机会话 ID，并将每轮用户消息和最终回答写入 SQLite。网页在本地保存该 ID；刷新后从服务端读取最近 20 条消息恢复显示，继续提问时服务端读取最近 10 条消息交给现有 ReAct Agent。点“新对话”会换一个会话。旧客户端首次请求仍可携带 `history`，已有会话则以数据库历史为准。

选择 SQLite 是因为当前数据是轻量、结构化的会话与消息；这一步验证“写入、取回、交给 Agent”的通路，不需要向量检索。这里的“短期”指同一会话的最近消息作为上下文，并不表示数据库会自动过期。跨会话偏好提取和语义检索尚未实现。

使用同一套 3 个固定离线场景运行 `python evals/memory_context_baseline.py` 和 `python evals/memory_context_baseline.py --after`，分别模拟只靠浏览器历史与刷新后携带会话 ID。[改动前原始结果](2026-09-28-memory-context-baseline.json)；[改动后原始结果](2026-09-28-memory-context-after.json)。

| 指标 | 改动前 | 改动后 | 变化 |
|---|---:|---:|---:|
| 必要上下文到达 Agent 边界的场景数 | 2/3 | 3/3 | +1 个场景（+33.3 个百分点） |

新增通过的场景是“刷新后只带会话 ID 继续提问”。这衡量的是上下文可用性，**不是回答正确率**。Agent 与 OCR 在测试中由替身代替；没有重测 DeepSeek 的准确率、延迟或 token 成本。OCR 服务仍不可用。需要评估实际收益时，用相同的合成销售数据和问题复跑真实模型，并比较工具参数、答案和耗时。

当前会话 ID 存在浏览器 `localStorage`，数据库没有自动清理旧会话；生产多用户使用前应加入用户身份校验和保留期限。图片轮次保存的是文字与文件名提示，不保存图片内容作为对话历史，因此刷新后能续接文字上下文，但无法把旧图片重新交给模型。

# Benchmark 构成与上下文验证：2026-10-02

## 数据从哪里来

不是完全合成的数据，也不应把所有部分都称为真实业务数据。

| 部分 | 来源和规模 | 执行方式与测量对象 |
| --- | --- | --- |
| OCR 候选集 | 用户提供的 sales 图片及 data.xlsx 校对标签，500张图、4,872行明细 | 图片/字段校验已做；OCR服务离线，尚未测识别质量 |
| SQL 查询基线 | 从上述数据按文件名顺序选择字段可用的20张单据、204行；程序生成19个关键词统计问题和1个无匹配问题 | 直接调用真实SQL工具，金额/行数与标准答案比较，不评价模型自主选工具 |
| 上下文/偏好基线 | 人工构造5个消息与偏好场景 | 替身模型捕获真实循环传入的消息，检查必要信息是否送达，不评价模型理解 |
| 运行保护基线 | 人工构造10个异常刺激，包括工具失败、重复/交替失败、调用预算与阻塞 | 脚本控制模型动作、注入故障，验证实际循环与保护代码；不能直接推导真实模型恢复能力 |
| 真实模型诊断 | 人工合成3行销售数据：2024甲公司100、2024乙公司200、2025乙公司900 | DeepSeek自主选择工具并回答；逐次记录参数、工具结果、回答、耗时，本次新增6个场景 |

因此固定离线基线共35个场景（20+5+10），真实模型诊断另报。用户提供的单据不是本项目评估程序合成的，但未核实其最初制作来源，不能据此宣称生产业务真实分布。用户说明这批图片完全未参与微调训练；尚未核对训练清单。

标准答案由标签中的票面金额与行数计算，保留Excel来源行号，并经独立内存SQLite核对。保留折扣金额、重复行和空值，不用数量乘单价重写标签。用户已接受按开具内容保留原值；这不等于逐图独立重标完成。原始图片与逐行标注只保留本地，不提交公开Git，也未发送给DeepSeek。

## 本次6个真实模型诊断

运行真实HTTP聊天接口、SQLite加载/保存、流式Agent循环与SQL工具。每个场景独立会话，只运行一次。前4例预置最近成功查询状态2024甲公司，并保存七轮无关对话，使原查询移出最近10条消息；后2例通过“记住：...”接口保存固定开头偏好，再在新会话中读取同一profile。评估实例timeout=20秒、max_retries=0，不改线上配置。

| 场景 | 人工核查的工具与回答 | 本次耗时 |
| --- | --- | ---: |
| 当前明确条件覆盖旧查询 | 2025乙公司，按公司分组，金额900；成功状态更新 | 8.059秒 |
| 只改年份、保留公司 | 2025甲公司，按公司分组，报告没有已确认数据；成功快照保持2024甲公司 | 2.392秒 |
| 新查询解除全部筛选 | 未传年份和关键词，按商品分组，完整总额1200；快照旧筛选清空 | 4.302秒 |
| 新话题解释Python列表 | 没调用工具，直接正确解释列表 | 0.942秒 |
| 跨会话读取固定开头偏好 | 2024甲公司100，回答以“统计结果”开头 | 2.772秒 |
| 当前要求覆盖长期偏好 | 同样查询100，回答按当前要求以“本次结果”开头 | 2.026秒 |

原始自动评分5/6，人工核查6/6。唯一自动失败来自评分器要求新全量查询必须group_by为空，而问题没有指定分组，模型按商品分组并使用全量summary正确回答1200。此项是评分口径过严，不是筛选继承或金额错误。原始JSON保留原始expected/checks；后续脚本只检查此例明确要求的年份/公司筛选与总额，不限制分组。没有通过修改Agent或再次调用模型获得“提升”。自动金额检查只检查回答中的数字，不能替代人工验证数字语义与完整性。

新增评分器测试检查错误年份、数字子串误判、偏好开头、错误事件及多余工具调用。全套43项测试通过，已有2个配置/依赖弃用警告。

## 目前能够说明什么

原35场景回归仍为SQL20/20、上下文信息送达4/5、运行保护10/10；运行保护从初始5/10增至10/10，是同套故障刺激上的+5项，不是总体任务成功率提升。当前6例是新增单次诊断，没有同例修改前结果，无法量化本批准确率、延迟或成本改进。实际token与费用尚未测量。

本次没有修改Agent业务行为。验证了明确新条件、解除筛选、新话题和两种偏好优先级在这些样例中的行为。未验证无匹配后进一步追问、含糊新话题、不同语言/措辞或并发请求。只保存最近成功查询，不能恢复任意更早任务。

当前测试集没有独立调参集/最终测试集划分，SQL子集也未随机或分层抽样。后续应按单据分组、考虑模板相似性划分，扩大自主任务类型并重复运行；工具正确、模型任务成功、异常恢复、OCR字段识别应分开评分。

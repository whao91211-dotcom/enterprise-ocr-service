# 主聊天链路的运行保护：2026-10-02

## 改动

保持现有 ReAct 流式循环，在正常工具执行路径增加运行保护。旧版 `ask`/AgentExecutor 不具备本次循环计数保护；模型网络配置共用。

- 相同工具和参数连续失败两次时停止。连续四次失败时停止，防止工具交替失败。成功调用会重置失败状态。
- 除原有八轮限制外，总工具调用预算默认八次，按实际调用逐个计数，包括同一轮的多个工具。
- 查询参数错误仍允许模型修正。无匹配数据是正常结果，不计为工具故障。
- OCR、修改、确认、图表和报告操作失败时停止，不自动重试写入；说明需要核对状态。
- 模型/工具等待超时或执行槽位已满时结束当前任务，保留明确的失败说明。

工具调用仍返回字符串，在内部附带失败标志；已知工具的错误前缀与异常被识别为失败。不是对任意第三方工具错误格式的通用解析器，新工具需补充错误契约。

## 超时语义与初版配置

模型等待期限 `AGENT_MODEL_TIMEOUT_SECONDS` 默认60秒；普通工具 `AGENT_TOOL_TIMEOUT_SECONDS` 默认60秒；总工具预算 `AGENT_MAX_TOOL_CALLS` 默认8。OCR 等待使用原有 `OCR_TIMEOUT_SECONDS` 加5秒，原有默认300秒未缩短。DeepSeek SDK 使用模型期限且关闭隐式重试。

这些默认值是可配置的初版运行策略，尚未经大规模时延数据选型。评估故障使用0.5秒配置，在2秒观察门槛内检查能否返回明确超时说明。

通过 daemon 线程限制调用者等待，**不是强制取消底层执行**。超时后底层写入可能仍然完成，回答要求先检查状态。最多四个调用可同时处于执行中；超时线程继续占用槽位直到完成，满载时拒绝新调用，不无限创建线程。这不是强制终止、事务回滚或跨进程任务管理方案。进程重启也不能据此保证外部操作已取消。

## 同一评估集复测

数据夹具与查询预期答案不变：20张图204行，35个评估场景。模型仍由替身提供故障请求，不评价真实模型恢复决策。结果是程序保护成功数，不是完整任务成功率。

| 指标 | 2026-09-30 | 2026-10-02 | 变化 |
| --- | ---: | ---: | --- |
| SQL 结果与预期一致 | 20/20 | 20/20 | 无变化 |
| 上下文传递 | 4/5 | 4/5 | 无变化，早期必要信息仍丢失 |
| 运行保护目标 | 5/10 | 10/10 | 增加5项，50%到100%，增加50个百分点 |
| 同一失败调用次数 | 8 | 2 | 减少6次，75% |
| 交替失败调用次数 | 8 | 4 | 减少4次，50% |
| 每轮3个失败调用的累计次数 | 24 | 2 | 被重复失败检测提前停止 |

最后一项不能单独证明总预算8次的作用；新增单元测试使用持续成功、参数不同的工具请求，验证总调用恰好达到8次后停止。

原先两个阻塞用例由评估程序终止；现在 Agent 自身返回超时说明，不需要评估程序终止等待。故障刺激未变，评估新增0.5秒配置覆盖；旧版本忽略该配置。增强了评分检查，必须收到“超时”的最终回答，且从阻塞开始到返回不超过2秒，不能把异常退出当通过。子进程返回自身计时，避免两个并行探针的读结果顺序影响计时。SDK内置超时、真实OCR耗时和底层线程取消不在该指标内。

34项单元测试通过。新增用例覆盖失败停止、成功调用总预算、工具/模型超时、写入失败不重试、只读参数可修正、OCR采用独立较长预算。修正评估加载器只恢复旧AgentExecutor导入入口，避免整个sys.modules快照回滚导致配置对象不同、模块反复加载。

## 真实模型诊断

复用三条合成销售记录和三个问题，只调用DeepSeek，不发送真实发票数据。金额与年份均正确，三个回答耗时7.646、2.607、1.914秒，单次诊断不用于稳定延迟比较。

两个回答将数量字段 `amount` 标签写成金额，虽然销售额 `sum` 的数值正确，仍属于回答字段语义问题。已在原始记录标记，不能宣称三条完整回答全部正确或整体回答质量提高。后续应明确数量/金额字段说明，并将标签正确性加入任务评分。真实模型在故障后的参数修正、备用线路选择和偏好遵循尚未系统评估。

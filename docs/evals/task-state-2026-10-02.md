# 成功查询的会话任务状态：2026-10-02

## 用户选择与范围

用户选择先结构化保存成功查询的年份、关键词、分组方式，再考虑模型对话摘要。本次只保存会话内最近一次成功 SQL 查询，不自动生成长期偏好，不建立通用历史摘要。

在 SQLite 新增 `chat_task_state`：按 session_id 保存 JSON 快照和更新时间，关联会话删除。查询工具完整输出能解析为已确认数据且匹配行数大于0时，提取工具名、年份、关键词和分组维度。不是解析给前端截断的2000字符片段，也不是从模型回答中猜测条件。超过200字的关键词不截断保存，跳过该次状态更新以免改变查询含义。

主聊天接口收到 task_state 事件时保存；下一次请求读取并传入系统上下文。失败或无匹配结果不覆盖最近成功查询。无筛选的成功查询会用空值覆盖旧年份/关键词，防止旧条件悄悄残留。新建会话使用不同 session_id，不继承状态。profile_id 的长期偏好不受影响。

历史状态不是当前请求的强制参数：当前请求和近期消息优先；新任务不自动套用旧条件，不明确时澄清。没有在代码中强制填写工具参数，实际继承正确性仍依赖模型，需要真实任务评估。

## 配对诊断

使用合成数据：2024年甲公司100、乙公司200，2025年乙公司900。先用真实SQL工具成功查询2024年甲公司，将结果提取的状态保存到SQLite。随后保存七轮无关对话，使最初查询移出最近10条消息；读取相同最近10条消息，对比不提供状态和提供状态。

| 观察 | 不提供状态 | 提供持久化状态 |
| --- | --- | --- |
| 模型输入中有年份和公司条件 | 否 | 是 |
| 一次真实DeepSeek诊断 | 合理要求补充年份/对象 | 调用rag_summarize，year=2024、keyword=甲公司、group_by=desc，回答100 |

无状态时澄清是安全行为，不是胡编。状态的价值在这一次诊断中表现为减少用户重新说明条件，不能从一个配对案例推导整体成功率或延迟提升。耗时7.583秒与2.420秒仅为当次记录；没有实际token和API费用测量。无真实发票数据发送给API。

39项单元测试通过，包含：状态经历历史截取后仍存在、不同会话隔离、空条件清除旧筛选、失败结果不提取；HTTP测试检查事件保存、刷新/多轮后的状态传递和新会话不继承。真实流式循环的状态事件另外由诊断脚本生成验证。

## 限制

- 只记最近一次成功查询，不能保证恢复任意更早的查询或全部历史要求。
- 未经工具验证的用户条件、无匹配查询、新话题识别、复杂多任务状态尚未覆盖。失败后最近消息优先于更旧的成功快照。
- 只覆盖 rag_query / rag_summarize；图表、报告和OCR任务状态不保存。
- 不改变最近10条消息的截取，也没有全文对话压缩。原35场景中的旧消息原文保留检查仍不能因这项改动直接算通过。

# Agent 上下文窗口与压缩前基线（2026-09-28）

运行 `python evals/context_window_baseline.py --output docs/evals/2026-09-28-context-window-baseline.json`。脚本使用当前 `run_agent_events` 真正组装出的 LangChain 消息，在模型边界用固定替身截获第一次及工具调用后的消息；所有历史、偏好、工具结果都是合成文本，不调用 DeepSeek、OCR 或企业数据库。[原始结果](2026-09-28-context-window-baseline.json)。

`tiktoken` 的 `cl100k_base` 只用于**代理 token 数**；它不是 DeepSeek 的实际输入 token、计费数或上下文上限。消息角色封装和供应商序列化未计入；工具定义单独按本地 JSON 序列化估算，固定为 1,331 个代理 token，不混入下面的消息文本数字。没有测量模型答案正确率、延迟或成本。

| 固定合成场景 | 当前模型消息文本代理 token | 关键观察 |
|---|---:|---|
| 2 条短历史后追问 | 459 | 早先的“2024 年”仍在历史中 |
| 14 条历史后追问 | 519 | 只保留最近 10 条，丢掉 4 条；关键年份不再出现于历史 |
| 2 条历史，其中一条回答很长 | 7,629 | 消息条数少并不意味着占用小 |
| 20 条合成偏好 | 4,274 | 系统提示从 421 增到 4,264 个代理 token |
| 一次长工具结果 | 第一次 425；第二次 9,261 | 工具结果完整 10,400 字符进入模型；界面事件仅显示前 2,000 字符 |

这五项是**上下文组成和保留情况**的测量，不是任务成功率。长历史场景说明固定“最近 10 条”可能省下文本却丢失任务约束；长回答和长工具结果说明只按消息条数设置窗口无法控制 token。大工具结果让第二次调用的消息文本增加 8,836 个代理 token，但不能据此推算 DeepSeek 实际费用。

后续选型应保持这套输入不变，分别尝试并比较：保留结构化任务状态（例如年份、公司、确认状态）、限制或摘要工具结果、按 token 预算挑选历史。每个候选方案都必须同时报告关键事实保留情况和代理 token 变化；有可用的真实模型调用时，再另测答案、工具参数、实际 token 用量、耗时与成本。OCR 仍不可用，不计入这次基线。

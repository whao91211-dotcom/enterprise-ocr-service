## 1. 项目目标与技术栈

项目面向销售单据的识别、核对、查询、统计与汇报。纸质单据图片经 OCR 提取字段，用户核对并确认后参与统计，随后可生成图表、Word、Excel、PPT。

当前是本机单用户工作区；没有完成多用户鉴权、大规模业务验证。更准确的业务称呼是“销售单据”，不能泛化为具备税务验真能力的发票系统。“海量数据”“定期自动清理”也不能在没有实现与证据时加入项目介绍。

## 2. 为什么选择 Agent，和 workflow、数据库界面有何区别

### 2.1 Agent 与 workflow

Workflow 由开发者预先定义步骤、分支和循环；Agent 让模型根据当前请求及工具结果选择下一步。Workflow 不会必然卡在 OCR，也能处理查询、修改和人工确认。

本项目用户可以从 OCR、修改、查询等不同入口开始，还可以提出“统计 → 画图 → 报告”的组合请求。因此采用迭代工具调用适配聊天交互。步骤固定的批量任务或月度报告可以优先考虑 workflow。

Agent 的代价是工具或参数选择可能出错，多次模型调用可能增加耗时和 token。项目将确定性业务规则放在程序中，再用执行保护限制模型行为。当前没有 Agent 与 workflow 的配对性能评估，不能宣称前者更快、更便宜或成功率更高。

### 2.2 Agent 与普通数据库网页

普通界面让用户选择功能、填写条件、点击执行；本项目让用户描述目标，模型将意图转换成工具和参数，并组合多步操作、处理追问。数据库仍承担存储和计算。

聊天框本身不构成 Agent；关键在于工具执行、结果回传和后续决策。精确修改适合表格，固定高频查询适合按钮，临时需求和跨工具组合适合自然语言入口。

“降低操作负担”是设计目标，尚未通过用户任务完成时间、操作次数、纠错次数等指标证实。

## 3. Agent 核心：工具定义、绑定、执行与回传

网页主链路是 `run_agent_events`，使用 `bind_tools` 加自定义循环。文件中另有旧 `build_agent` / `AgentExecutor` 入口，不能把旧入口的行为与网页主链路混为一谈。

```text
用户请求
  → 系统规则、近期历史、状态、偏好与工具定义
  → DeepSeek 返回 tool_calls
  → Python 查找并执行工具
  → ToolMessage 回传真实结果
  → 再次调用模型
  → 继续工具调用或输出最终回答
```

### 3.1 工具如何定义

```python
@tool
def rag_summarize(group_by: str = "item", keyword: str = "", year: str = "") -> str:
    """统计已确认销售数据；说明用途与各参数含义。"""
    ...
```

`@tool` 将函数包装成工具对象；类型、默认值形成参数结构；docstring 说明用途。模型获得工具说明和参数 schema，不是函数体执行能力。

### 3.2 bind_tools 与工具路由

```python
llm_tools = get_llm().bind_tools(_TOOLS)
_TOOL_BY_NAME = {t.name: t for t in _TOOLS}
```

`bind_tools` 配置可用工具，不会当场执行它们。模型响应提供 `name`、`args`、`id`；程序通过映射找到工具，用 `fn.invoke(args)` 执行。未知工具返回失败。

```python
messages.append(assistant)  # 包含工具调用的模型消息
messages.append(ToolMessage(content=result, tool_call_id=tc["id"]))
```

调用 ID 将结果关联到具体请求。模型可读取结果继续决策，真正访问数据库、写文件的是 Python 工具。

`_guess_intent` 主要生成界面意图事件；实际工具选择读取模型的 `tool_calls`。本项目可称为 ReAct 风格迭代工具调用，不能宣称展示或保存了模型内部完整思维过程。

来源：[主循环](../agent/agent.py)、[模型封装](../agent/llm.py)、[查询工具](../tools/rag_tool.py)。

## 4. 每轮上下文与 Memory

### 4.1 初始模型输入

工具定义经绑定配置；消息列表为：

```text
SystemMessage：业务规则 + 字段说明 + 任务状态 + 显式偏好
最近历史：HumanMessage / AIMessage
HumanMessage：当前请求
```

规则指导工具路由、年份传参、核对和完成声明。字段词典解释 `amount` 是数量、`sum` 是票面金额，避免自然语言标签误读。提示规则不替代程序校验。

上传图片时，DeepSeek 获得的是本地路径文本；OCR 工具读取图片并发送给 OCR 服务。路径文本不等于图片像素已传给 DeepSeek。

### 4.2 历史选择与超限

聊天入口调用 `load_messages(session_id, limit=10)`，新会话取 `history[-10:]`；Agent 再取 `history[-10:]`。是最近10条消息，通常约5轮一问一答，不是10轮，也不是模型 token 容量。

```sql
SELECT role, content FROM (
  SELECT id, role, content FROM chat_messages
  WHERE session_id = ? ORDER BY id DESC LIMIT ?
) ORDER BY id;
```

内层取最新消息，外层恢复时间顺序。被舍弃的消息仍在数据库中，不发送给本次模型调用。10 是固定初始策略，没有证明最优的窗口大小对比。

本轮工具调用及完整结果继续追加，无动态 token 裁剪。网页只展示 `result[:2000]`，模型仍收到完整 `result`。系统提示、工具 schema、偏好和长消息都可能占用大量输入。

当前无完整输入预算、输出预留、超限专项压缩和重试机制。若调用因超限抛出异常，走通用模型失败路径并停止；没有现场验证具体供应商的超限响应。

### 4.3 三类记忆

| 类型 | 存什么 | 使用方式 |
|---|---|---|
| 对话历史 | 用户请求、最终回答及卡片元数据 | 最近10条文本进入模型；网页可分页查历史 |
| 任务状态 | 最近一份有匹配查询的工具、年份、关键词、分组 | 按会话持久化，作为续问参考 |
| 显式偏好 | 用户主动要求保存的习惯 | 按 profile 读取并注入，最多20条 |

任务状态从成功结构化工具输出提取，而非任意旧对话摘要；无匹配、失败不更新，不包含业务数值。当前请求和近期信息优先，不能把旧查询条件自动用于新任务。

`记住：…`、`忘记：…`、`查看记忆` 由确定性命令解析。没有自动从全部聊天中推断并保存偏好。profile ID 是组织标识，不是鉴权凭据。

### 4.4 重要信息丢失仍未完全解决

按时间截取不等于按重要性筛选。现有任务状态只补部分查询条件，不能完整保存早期任务目标、特殊约束、多任务和状态失效；第一次工具调用已漏掉的条件也不能靠工具结果提取补救。

后续方向：维护当前有效任务目标、条件、约束和取消/切换规则；重要状态持续提供，历史按预算选择。该方案未实施。验证应覆盖历史挤出、条件覆盖、取消任务、新任务、多任务、无匹配续问，报告参数正确率、约束遵守率、任务成功率和 token。

来源：[聊天入口](../web/agent_chat.py)、[历史存储](../db/chat_memory.py)、[状态提取](../agent/task_state.py)、[任务存储](../db/task_state.py)、[偏好](../db/preference_memory.py)。

## 5. 关系数据库与向量数据库的选择

本项目没有向量数据库或 embedding 检索链路。名称包含 `rag` 的工具实际是 SQL 查询，不是向量 RAG。

| 需求 | 更适合的能力 |
|---|---|
| 明确年份、公司、状态筛选，全量统计，可靠更新 | 关系数据库 |
| 大量文本中寻找语义相关片段、相似案例或图片 | 向量检索 |
| 当前任务必须遵守的条件 | 明确的结构化状态，不只依赖相似度召回 |

OCR 后销售字段结构化，金额必须覆盖全部匹配记录；不能用相似度召回的 top-k 样本代替全量统计。当前偏好少、用户归属明确，可以直接按 profile 查询，不必增加语义检索。

长期记忆不等于向量数据库。大量跨会话经验出现后，可以考虑“原始记录与有效状态持久化 + 向量候选检索 + 用户归属/时间/失效过滤”。相似度不证明事实正确或约束有效。向量能力也可与关系数据库结合，不一定部署独立服务。

还未比较不同记忆方案的质量、延迟或费用。未来评估相关记忆召回率、误用旧约束率和最终任务成功率。

## 6. SQL 输出摘要：计算和展示分离

### 6.1 统计工具

`crud.summarize_confirmed` 用 SQL `WHERE`、`GROUP BY`、`SUM`，取得全部分组并按金额降序排列，聚合 SQL 没有20组限制。

```python
summary = {
    "total_rows": total,
    "total_amount": round(sum(g["amount"] for g in groups), 2),
    "total_sum": round(sum(g["total"] for g in groups), 2),
}
selected = groups[:20]
```

SQL 计算各分组，Python 累加全部分组生成全量总计，再截取展示组。400条、40组中只展示20组，不改变全量总计；模型不能将展示组之和当总额。

输出保留 `source`、`filters`、`summary`、总/返回/省略组数、`columns + rows`、字段含义和展示说明。JSON 使用紧凑分隔符；不能泛化为 JSON 总比自然语言省 token。

### 6.2 明细工具

`rag_query` 在 SQL 中直接 `LIMIT 20`，按日期和 ID 排序，再单独查询匹配总行数。`top_k` 只是条数上限，不是语义相似度排序。明细样本不能计算全量金额，目前没有分页，更多数据需缩小范围或通过完整办公导出查看。

### 6.3 历史测量与取舍

400条2024年已确认合成数据，40商品各10条，每条金额10；另含其他年份与待确认干扰记录。真实SQL工具输出由 `cl100k_base` 编码，不调用模型/OCR。

| 场景 | 改动前代理token | 摘要后代理token | 减少 |
|---|---:|---:|---:|
| 默认20行明细 | 1061 | 922 | 139，13.10% |
| 请求400行明细 | 20821 | 922 | 19899，95.57% |
| 40个分组 | 932 | 395 | 537，57.62% |

这不是无损压缩、整次输入、实际DeepSeek token或成本；大幅减少主要包括省略信息。后续增加字段说明，同场景历史记录为明细970、分组469。字段语义清楚比盲目追求最短更重要。

当前限制：行数不等于token上限；长字段仍可能很大；无匹配返回文字、成功返回JSON；统计分组与行数计数不在同一读取快照，数据变化时潜在不一致尚未复现。被省略分组须重新查询，不能猜测金额。

## 7. OCR：识别、校验与原子替换

上传接口检查扩展名和非空，保存UUID文件名，传本地路径给Agent。扩展名检查不是完整图片内容验证，也未据此证明上传大小治理完整。

OCR客户端根据配置选Qwen JSON或InternVL CSV，图片转base64 data URL后请求服务。固定8字段；提示保留原语言、负号、折扣和票面金额，不从数量×单价重算，也不猜模糊内容。

检查HTTP状态、响应结构与截断标志；`finish_reason='length'` 拒绝入库。Qwen要求每行恰好8键、字符串/null、非全空；InternVL CSV容错更宽松，校验强度不同。

格式正确不代表内容正确。识别成功先入库为 `pending`，然后展示核对卡片。

```python
conn.execute("BEGIN IMMEDIATE")
# 查找或创建单据
conn.execute("DELETE FROM ocr_rows WHERE doc_id=?", (doc_id,))
_insert_rows(conn, doc_id, rows)  # 新行全部pending
# 增加版本
conn.commit()
# 任何异常：conn.rollback(); raise
```

删除与插入同事务，重识别中途失败保留旧行。成功重新识别不能沿用旧确认状态。按保存文件名定位；重复上传相同图片生成新UUID，不能宣称已做内容去重。OCR逐行摘要仍可能很长，没有SQL工具的20行展示限制。

来源：[OCR客户端](../tools/ocr_client.py)、[OCR聊天工具](../agent/agent.py)、[原子替换](../db/crud.py)、[OCR验证](evals/2026-10-03-ocr-revalidation.md)。

## 8. 人工确认、修改、事务与版本控制

### 8.1 入库不等于统计准入

```text
OCR成功 → pending入库 → 用户核对/修改 → 明确确认 → confirmed → 参与统计
```

实际修改成功：`confirmed → pending`；重新确认：`pending → confirmed`。只说想修改、修改失败或值未变化，不触发相同状态重置。

模型可辅助检查，最终核对由当前业务流程交给用户。SQL固定过滤confirmed，执行统计准入规则；人工确认不保证所有数值100%正确。

确认工具入口尚未见独立授权校验：模型若未经用户允许调用确认，状态过滤无法阻止已被改成confirmed的记录。仅静态观察，未完整复现或审计所有入口。

### 8.2 共享修改层

聊天工具与核对表共用 `review.save_edits`，统一字段检查、事务、pending重置和版本更新。允许8字段、有限长度；数字用Decimal检查是否有限，检查不等于业务内容正确，也不等于全项目Decimal计算。

批量先规范化输入，再在事务中校验行归属并更新；有实际变化才增加单据版本。保存后重新读取结果用于展示。当前变更描述不等于完整持久化审计日志。

### 8.3 自动回滚

同一事务内未提交修改遇异常全部撤销。`with conn` 正常退出提交、异常退出回滚；关闭连接是资源清理，不是这段实现中决定提交的机制。若循环内逐行commit，已提交部分不能靠后续事务回滚撤销。

回滚覆盖字段、确认状态和同事务版本变化，不自动删除外部文件，也不因Agent等待超时自动发生。

### 8.4 为什么不用互斥锁代替版本号

互斥让保存串行，但A/B先读取旧金额后各自串行保存，仍可能旧请求覆盖新结果。版本号识别请求过时；数据库事务保证一次操作原子性。

网页保存/确认传 `body.version`；事务内比较当前版本，冲突返回409；成功修改或确认后增版本。人工编辑期间不长期持锁，避免用户思考/离开时阻塞所有操作。

SQLite写事务协调数据库写入；Python锁只保护使用同一对象的进程内共享状态。聊天的 `_SESSION_LOCK` 用于会话活动登记，不提供全数据库或跨进程锁保护。

当前聊天修改传 `expected_version=None`，聊天确认也未传预期版本，不能宣称所有入口都有旧版本保护。多入口覆盖风险尚待验证。

来源：[核对数据层](../db/review.py)、[聊天核对工具](../tools/correct_tool.py)、[表格接口](../web/product.py)、[回归测试](../tests/test_product_review.py)。

## 9. 执行保护与完成声明

`ToolOutcome` 是附带 `failed` 和 `cards` 的字符串；程序据失败标志控制循环，模型读取文字。一部分失败依赖已知文本前缀，新增工具需补错误契约；无匹配不是故障。

| 机制 | 当前规则 | 边界 |
|---|---|---|
| 重复失败 | 同工具同参数连续失败2次停止 | 不保存全部失败历史 |
| 连续失败 | 连续4次失败停止，成功重置 | 不自动保证正确恢复 |
| 副作用失败 | OCR、修改、确认、生成等失败停止 | 不盲目自动重试；未实现通用幂等机制 |
| 轮数与调用预算 | 最多8轮模型调用，工具总预算默认8 | 不是token、金额或整体耗时预算 |
| 等待超时 | 模型/普通工具默认60秒，OCR独立配置加5秒 | 初始可配置值，未证实最优 |
| 资源槽位 | 最多4个bounded_call同时执行 | 卡住线程可能长期占槽 |

`bounded_call` 在daemon线程中执行，通过队列限时等待。超时不强制取消底层线程，写入或文件生成仍可能稍后完成，所以先核对状态再重试。

主循环记录本轮修改成功证据和文件生成证据。模型无工具成功结果却说“已修改/已生成”时，首次追加纠正规则，再次违规则停止。文字正则、修改布尔标记、文件存在检查都有限：不验证每行是否满足请求，也不完整覆盖任意完成声明或文件内容。

历史同一离线故障集：保护目标5/10→10/10；相同失败调用8→2（减少75%）；交替失败8→4（减少50%）。这是模型替身控制的程序保护，不是总体任务成功率或真实模型恢复质量。

来源：[保护模块](../agent/runtime_guard.py)、[主循环](../agent/agent.py)、[配置](../config.py)、[运行保护评估](evals/runtime-guards-2026-10-02.md)。

## 10. 多格式数据快照与工具协作

相同查询条件不保证不同时间查询得到相同数据。先生成Word后数据改变，再生成Excel会产生口径差异。

`capture()` 在读取事务中获取全部已确认匹配明细；围绕同一份rows计算商品、公司、日期分组及全量总计；保存条件、时间、rows、groups、summary。

第一个生成工具登记文件及快照，返回 `snapshot_id`；后续生成工具传该ID复用。当前ID实际是关联快照的文件登记ID，不是独立快照实体ID。显式年份/关键词与原快照冲突时拒绝复用。

模型负责传ID，程序负责读取和检查。模型漏传时仍分别读取最新数据；不能说同请求自动强制绑定快照。要求“最新”应重新取数据，旧快照一致但可能过时。

| 输出 | 展示范围 |
|---|---|
| Excel | 全部匹配明细与分组，图表前15组 |
| Word | 全量总览，分组表前15组 |
| PPT | 全量总览，分析图前10组 |

文件由固定程序模板生成，不是任意自由文档编辑。三个工具不是一个事务，部分成功文件保留。快照用Decimal累加后转float，Word又基于float分组求和，需验证精度边界；`number()` 将解析异常当0可能静默隐藏问题，尚待评估。

历史一次真实模型三格式任务通过5项检查，12.765秒，不能推出整体成功率或速度提升。

来源：[快照服务](../services/sales_snapshot.py)、[办公工具](../tools/office_tool.py)、[Word工具](../tools/report_tool.py)、[升级验证](evals/product-upgrade-2026-10-03.md)。

## 11. 文件登记、SSE、预览与恢复

文件生成后验证存在与类型，登记UUID、路径、类型、快照和预览状态。网页使用登记ID下载/预览；随机ID不是鉴权。

Agent `yield` 工具调用、结果、卡片、回答等事件；FastAPI封装 `data: JSON\n\n` 并以 `text/event-stream` 输出。前端POST fetch读取流，按事件更新进度与卡片。

主循环用 `invoke`，主要是步骤事件流，不是逐token回答。过程反馈不等于推理速度提高。前端epoch忽略切换会话后的旧事件，避免结果展示到错误会话；不代表取消后台任务。

后端保存用户/最终回答与卡片ID，刷新后按ID恢复，不重新生成。文件被删除则卡片不可用。异常/中断时尝试保留已产生卡片，但没有持久化执行轨迹的任意断点续跑。

生成与预览分开：Word/PPT通过独立Office进程转PDF，PDFium渲染；Excel是分页数据预览而非完整Office样式。预览串行、有队列限制和60秒转换期限；失败仍可下载原文件，重试只转换预览。

当前无SSE事件ID重放、服务重启后步骤恢复或文件生成/登记/消息存储的整体原子性；中途退出可能留下未关联结果。Office预览依赖本机环境，不等于已可直接部署任意服务器。

来源：[文件登记](../db/artifacts.py)、[聊天接口](../web/agent_chat.py)、[前端](../web/static/app.js)、[预览](../services/office_preview.py)。

## 12. 替身模型与分层评估

### 12.1 替身如何实现

```python
class ScriptedModel:
    def __init__(self, calls=None):
        self.calls = calls or []
        self.messages = []
        self.steps = 0

    def bind_tools(self, tools):
        return self

    def invoke(self, messages):
        self.messages.append(list(messages))
        self.steps += 1
        calls = self.calls[self.steps - 1] if self.steps <= len(self.calls) else []
        return AIMessage(content="" if calls else "替身回答", tool_calls=calls)
```

替身满足主循环接口，不调用API、不理解问题。预设每次调用，记录收到的上下文。测试通过以下代码替换Agent实际引用的模型工厂：

```python
with patch.object(agent, "get_llm", return_value=model):
    events = list(agent.run_agent_events(question))
```

替换范围结束后恢复真实函数。可保留真实编排/工具，也可按故障目标替换工具。重复失败测试安排超过阈值的失败序列，避免替身自行结束掩盖保护失效；阻塞模型模拟不返回，用短等待配置验证超时说明。

替身证明程序应对指定刺激的行为，不证明模型自主决策、偏好遵循或任务恢复质量。

### 12.2 测试层次

| 层次 | 验证内容 |
|---|---|
| 单元/契约 | 字段、SQL、状态、事务、版本 |
| 编排/故障注入 | 重复失败、预算、超时、副作用失败停止 |
| 集成 | HTTP、数据库、OCR响应、文件登记和界面连接 |
| 真实模型离线 | 工具选择、参数、结果、回答与业务状态 |
| 多轮/边界 | 历史截断、新任务、条件变化、未经授权操作、诱导内容 |
| 性能/恢复 | 实际token、费用、P50/P95、并发、资源占用、中断 |
| 上线与监控 | 小范围发布、版本回退、线上轨迹和失败回归 |

后几层是生产建设方向，不代表本项目都完整实施。框架可辅助采集轨迹和评分，但不替代业务验收标准。

### 12.3 评分原则

- 先定义预期结果，合成数据加干扰项，避免只有简单成功路径。
- 同时检查工具选择、参数、真实结果、最终回答；修改查数据库，文件查实际交付物。
- 数值/状态用确定性断言；语义判断辅以人工或校准后的模型裁判。
- 不强制唯一合理工具顺序；检查必要动作、禁止动作、依赖和最终状态。
- 测试集与调试集分开；重复运行、措辞变化、新案例分别报告。
- 留存模型/提示版本、输入、工具参数与结果、耗时、token和失败证据；生产轨迹需考虑敏感数据管理。
- 自动测试项数、故障保护通过率、真实任务成功率、代理token是不同指标。

### 12.4 历史结果边界

| 结果 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 已记录110项自动测试通过 | 对应版本回归检查 | 业务准确率100% |
| 单次OCR完整流程7/7 | 修复后一次合成单据流程步骤通过 | 总体准确率、所有三格式交付覆盖 |
| 已知缺口5/6→6/6 | 同套6例单次核心指标多通过1项 | 总体成功率、独立测试集泛化 |

## 14. 面试表达：将选择、实现和证据连起来

每个亮点使用同一结构：具体问题 → 为什么这样设计 → 如何实现 → 测量/验证 → 代价与局限。

项目概述参考：

> 项目面向销售单据核对与汇报。我使用DeepSeek和LangChain工具调用搭建迭代执行链路，连接OCR、人工核对、SQL统计以及图表和办公文件生成。识别结果先以待确认状态入库，确认后才能进入统计；修改后重新待确认。程序通过事务、调用预算、重复失败检测和超时保护控制执行过程，并用会话历史、查询任务状态和显式偏好支持连续交互。工具输出摘要在400条合成记录、40分组的历史评估中将代理token从932降至395，但这不是实际费用下降；当前还有任务约束保留、授权与版本边界等待完善问题。

常见问题回答要点：

- 为什么Agent：任务入口和组合不固定；固定任务可用workflow；没有配对证据就不声称性能优势。
- 为什么SQL：结构化字段需要明确筛选与全量统计；向量召回不能代替全量金额聚合。
- 为什么确认状态：持久化和统计准入分开；人核对内容，程序执行准入规则；授权入口仍需验证。
- 为什么事务：一次批量操作整体提交，失败保留旧数据；超时不意味着自动回滚。
- 为什么版本号：锁防并发写，版本防旧请求；聊天入口保护范围不同。
- 如何优化：程序聚合、紧凑表格、限制展示、保留总额与省略标记；存在信息损失与未测的真实质量/成本影响。
- 如何验证：先程序测试和替身故障注入，再真实模型任务、多轮与文件验证；指标分层，保留失败，未测的就明确说未测。
